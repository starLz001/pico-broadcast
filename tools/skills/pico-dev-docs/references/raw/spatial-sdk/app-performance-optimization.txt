性能优化
========================================
性能优化是空间应用的开发中重要的一环，并且会贯穿整个应用开发周期。它不仅决定了用户的沉浸感和交互流畅度，也直接关系到设备的续航、可扩展性等方面。通过合理的性能优化，应用才能保持高帧率和低延迟运行，兼顾流畅体验、能效和可扩展性，从而提升用户体验。
*性能优化工作流
在实际的性能优化工作中，往往会分为这样几个步骤：
*检查性能问题：通过各种性能调试工具或其他手段，发现应用中存在的性能问题并分析，从而找到影响性能的瓶颈。
*优化性能表现：针对发现的性能瓶颈进行修改，优化性能表现。
*持续监控性能：为对用户体验有明确影响的部分以及已经发现了的性能问题制定基准指标，在研发流程中和线上持续进行监控。
*检查性能问题
发现性能问题有多种手段，可以通过人工分析来发现新的性能问题，也可以通过性能基准测试来发现已有性能指标的变化，还可以通过测试、用户反馈等渠道来收集性能相关反馈。
*

*
在完成优化之后，可以再次进行分析以验证优化的效果。同时也需要留意，在优化一处性能表现后，要避免引入其他的性能问题。
*持续监控性能
完成性能优化之后，可以将这处问题编写成性能测试的用例，并加入到定期执行的性能测试中，来避免相同的问题再次发生。同时对于已经上线的空间应用，也要持续关注用户反馈和线上监控发现的性能问题，并对其进行分析和优化。
*如何优化 3D 场景
*在一个可视空间中，同时存在的 3D 元素总量与视觉渲染压力的综合结果可称为“场景复杂度”。
*在空间应用中，“三维场景复杂度” 是影响性能、沉浸感与兼容性的核心因素。过高的复杂度可能导致性能下降（如掉帧、卡顿），过低则会削弱沉浸感。你需要结合平台性能上限与内容设计目标，在真实感与流畅性之间找到最佳平衡，使用户能在流畅的体验中自然沉浸于应用的内容。
*本文将介绍何为场景复杂度、PICO 所支持的上限，以及如何优化场景。 
*影响场景复杂度的因素 & 优化方式
*一个场景的复杂度受到很多因素的影响，包括模型数量、三角面数量、纹理大小等。
*模型数量
*模型（Model）数量指的是在一个三维虚拟空间（即场景）中，所有独立 3D 物体的总和。场景中的每一个可以被单独识别、移动、或操作的物体，都算作一个模型。

*建议的优化方式：
**
*三角面数量
*所有复杂的 3D 模型，无论其表面看起来多么圆润或不规则，其最底层的基本构成单位都是三角面（Triangle）。三角面具有以下特点：
*绝对平面性：三个点永远可以定义一个唯一的平面。
*计算简单高效： 三角形是最简单的多边形，其几何计算（如面积、法线方向等）对计算机来说非常快速。
*无数个这样的三角面以不同的角度和位置拼接在一起，就构成了一个复杂的 3D 网格（Mesh），从而模拟出真实物体的表面。
*建议的优化方式：
**
*纹理大小
*在 3D 场景中，纹理（Texture）大小是指所有用于物体表面贴图的图像资源在运行时占用的内存大小。你可以把纹理看成 “贴在模型表面上的皮肤”。一个模型可能只是一个简单的立方体，但贴上一张高清纹理后，它就能看起来像是木箱、金属箱或石头箱。
*纹理内存 = 宽 × 高 × 通道数 × 每通道字节数：
*512 x 512：较低分辨率，适合次要物体。消耗大约 1MB 内存。
*2048×2048：高清纹理，用于主角或近景物体。消耗大约 16MB 内存。
*建议的优化方式：
**
*光源和阴影数量
*光源决定了场景中的内容是否可见，而阴影则影响场景的真实感与空间感。
*如果你的场景的光照不会动态变化，那么就可以通过基于图像的光照（IBL）或者光照烘焙等手段来达到几乎相同的光影效果，从而避免运行时的动态光照带来的性能开销。
*建议的优化方式：
**
*动态渲染
*动态渲染是指角色或物体在场景中持续运动的过程，例如人物走路、手部摆动、门打开、箱子旋转等。为了让场景 “动起来”，系统需要消耗额外的CPU算力来控制和计算动画当前的状态，同时也需要更多GPU能力来实时渲染物体的最新内容。
*建议的优化方式：
**
*物理模拟
物理模拟（Physics Simulation）用于让场景中的物体 “看起来真实”，如掉落、碰撞、弹跳、重力感应等。对于物体新的位置，旋转，缩放以及其他相关的属性，都需要系统使用大量的CPU能力来进行计算。
*建议的优化方式：
*
*三维交互
*三维交是指用户与场景之间的响应关系，系统需要追踪用户的行为，比如头部的、眼睛的、手部的，以及其他外部设备的输入，例如手柄、键盘等等。然后根据用户的输入，系统还需要更新对应被交互的物体的状态，例如点击开门、拖动物体、靠近后触发对话等。

*总结
在空间应用中，决定三维场景复杂度的元素并非仅局限于上述几个方面，上述内容只是影响场景复杂度的核心要素。 不同元素对GPU和CPU的要求也各不相同：
*
*不同复杂度的场景
为了更直观地理解三维场景的复杂度，结合平台所支持的技术上限以及实际开发需求，场景的复杂度可以分为低、中、高三个级别。
*低复杂度场景
*组成元素：20 以内个物体
*三角面数量：10 万左右
*贴图分辨率：中等（≤2048x2048）
*光照方案：单个实时光源 + 多个烘焙光源
*适合用途：入门级体验、交互演示、静态展示
*中等复杂度场景
*组成元素：50 个以内物体，2~3 个可以互动角色
*三角面数量：20 万左右
*贴图分辨率：中等（≤2048x2048）
*光照方案：使用最多 2 个实时灯光，其余为烘焙或环境光
*适合用途：生活类体验、剧情式内容
*高复杂度场景
*组成元素：50+ 物体，一个天空盒
*贴图分辨率：中等（≤2048x2048）
*三角面数量：30 万+
*光照方案：一个动态光源
*适合用途：自然漫游、教育类体验、放松类场景

方式

描述

人工分析

通过 PICO Spatial Profiler、Android Studio Profiler 和 Prefetto 等工具来分析空间应用，可以通过多个方向来进行分析：
*通过记录 System Trace 或者更详细的 Callstack Sample 或者 Method Recording，分析应用卡顿时程序的执行状况，找到相应瓶颈所在。
*通过 Heap Dump 和内存分配记录，分析应用内存占用情况和发现内存泄露。
*通过 PICO 在 Trace 记录中提供的空间应用性能数据，分析应用的空间应用特性使用情况。
*甚至可以通过 Android 提供的 Trace API，添加自己的 Trace 记录，来分析自己应用中重要流程的运行时长和状态。

性能基准测试

可以通过 Androidx Benchmark 来编写性能基准测试，并定期运行（比如在 CI 流程中）来持续对这部分性能指标做监控。关于 Androidx Benchmark 详情请参阅官方文档。



方式

描述

*资产优化

降低场景复杂度、压缩贴图、烘焙光照等合理的优化可以在几乎不影响表现的情况下明显降低渲染场景的开销。

*资源懒加载

不要在初始化时就加载好所有所需资源，这样只会减慢应用的启动速度，并增加应用运行时的内存开销。

*资源预加载

在用户操作之前，提前加载好下一步场景所需的资源，就可以有效降低用户操作后的等待时间。良好结合懒加载和预加载可以平衡运行时资源占用和用户等待时间。

*异步、多线程计算

将繁重的计算从主线程转移到其他线程中，避免长时间占用主线程导致卡顿。



*问题类型

*优化建议

*示例

物体过多

*移除不必要或纯装饰性的物体，专注于核心物体以降低多边形数量和渲染负担。
*保留对场景表达或功能至关重要的物体，确保空间布局清晰、逻辑明确。
*建议在整个场景中，带有 skinned mesh 的模型不超过 15 个。

移除桌面上的零散文具、书本或装饰花瓶，仅保留沙发、桌椅等关键家具。

场景规模大，内容复杂

*将大型场景拆分为多个子区域，根据摄像机或玩家位置动态加载和卸载区域（Streaming/分区加载）。

仅加载玩家当前所在的房间或区域。当玩家走向门口的触发器时，系统开始加载相邻的区域，并卸载玩家已离开的区域。

被遮挡物体造成渲染资源浪费

启用遮挡剔除 (Occlusion Culling)，让渲染引擎在渲染前判断物体是否被其他不透明物体完全遮挡。

即使摄像机前方有整栋建筑，建筑内部不可见的家具不会被渲染，从而节省 GPU 资源。

绘制调用次数过高

* 静态批处理 (Static Batching): 将场景中共享相同材质的静态物体合并成一个更大的网格。
* GPU 实例化 (GPU Instancing): 对于需要大量重复渲染的相同网格（如植被、子弹），使用 GPU 实例化技术，通过一次绘制调用渲染所有内容。

*静态批处理：将餐厅里所有的静态桌椅合并为一个物体，从而将多个绘制调用减少为一个。
*GPU 实例化：渲染一片森林时，对所有相同种类的树木模型启用 GPU 实例化，可以用极低的 CPU 开销高效绘制成千上万棵树。



指标

描述

面数

模型的面数指模型的网格所包含三角面的数量，对于同一个物体，面数越多模型就会越精致，反之就会越粗糙。但增加面数会增加模型在内存/显存中的体积，增加渲染压力。

*纹理数量和分辨率

纹理是贴在模型表面上的图像，对于同一个模型，纹理分辨率越高，模型显示就会越清晰，反之就会越模糊。而同一个模型可以同时使用多张纹理贴图，对应于模型的不同位置。增加纹理的数量和分辨率也会增加模型在内存/显存中的体积。

*材质数量和类型

材质通过着色器来计算模型上的纹理的显示效果，不同类型的材质以及不同的参数设置都会改变最终的渲染结果。同一个模型可以同时使用多个材质，对应模型不同位置或者实现特别的渲染效果。相比简单的材质（比如 Unlit 材质），使用复杂的材质（比如 PBR 材质）就会带来额外的 GPU 计算开销。

*骨骼数量

骨骼数量指模型中骨骼的数量，骨骼越多就可以越精细地控制模型的变化。而增加骨骼数量会带来更大的 CPU 计算开销。



*问题类型

*优化建议

*示例

面数过多

*减少模型面数，精细度根据实际场景决定。
*使用法线贴图增强细节，而无需增加面数。
*控制单个空间容器内的模型总面数：
*Shared Space：175000
*Full Space：350000

*小物体或远处装饰物使用低面数模型，不影响整体效果。
*角色服饰褶皱、石墙凹凸感用法线贴图代替高面数建模。

*纹理数量过多且分辨率高

*合并多个纹理，减少调用次数。
*对纹理进行合理压缩，降低体积和运行压力。

*将多个 UI 按钮合并到一张纹理图集 (Texture Atlas) 中。
*把草地碎片、石头等零散小贴图合并成大纹理，减少 Draw Call。

*材质数量过多且类型复杂

*优先使用简单材质，或简化 Shader Graph。
*无需实时光照或已烘焙光照时，选用 Unlit 材质优于 PBR 材质。

*远景建筑群使用 Unlit 材质替代 PBR 材质，性能更优且视觉差异不大。
*已通过 Lightmap 烘焙的物体无需使用实时光照 + PBR 渲染。

骨骼数量过多

在合理范围内减少骨骼数量，兼顾动画需求和性能。建议单个模型的骨骼数量不超过 72 个，且单个顶点对应的权重骨骼不超过 4 个。

远景 NPC 仅保留躯干和四肢骨骼，省略细节骨骼，减少计算量。



*问题类型

*优化建议

*示例

模型面数过高

*使用细节层次（Level of Detail, LOD）方案，为同一物体创建高、中、低精度版本，根据摄像机距离或屏幕占比自动切换显示最合适的模型。
*对高面数模型，借助自动减面工具生成低精度版本，提高效率。

当玩家靠近一辆汽车时，显示拥有 50,000 个面的高精细模型 (LOD0)；当汽车距离稍远时，切换到 10,000 面的中等模型 (LOD1)；当它在视野中只是一个小点时，则使用仅 500 面的低精度模型 (LOD2)。



*问题类型

*优化建议

*示例

纹理资源开销大

*调整分辨率：根据物体的重要性和可见尺寸，使用恰当的贴图尺寸，避免浪费。
*纹理压缩：使用硬件支持的压缩格式（如 ASTC, ETC2）大幅减少显存占用和带宽需求。
*纹理图集：将多个小贴图合并到一张大图集中，允许多个模型共享同一材质，从而减少绘制调用。
*复用：创建通用的纹理，并在多个不同物体间复用。

*分辨率：一个远处的建筑或一个小道具使用 512x512 贴图，而主角色的贴图则使用 2048x2048 贴图。
*压缩：将纹理的原始纹理转换为平台对应的压缩格式。
*图集：将一个角色身上的盔甲、靴子、手套等小部件的贴图全部合并到一张图集中，使整个角色只需一个材质即可渲染。
*复用：场景中所有的木质家具（桌、椅、柜）都共用一张高质量的 “木纹” 贴图。



*问题类型

*优化建议

*示例

光源数量过多

*精简场景中的光源数量，严格控制实时计算光源，避免性能浪费。
*保留关键光源，确保核心场景的亮度和视觉效果。
*对非必要或装饰性光源禁用实时光照，可用烘焙光照或环境光替代。

在室内场景中，仅保留一盏顶灯作为主光源，其余装饰性壁灯、射灯禁用实时光照。

实时阴影开销大

*优化实时阴影设置，例如降低阴影分辨率、缩短阴影绘制距离，减轻 GPU 负担。
*对非关键物体关闭阴影投射功能，或使用静态烘焙阴影替代。

*保留主角和关键 NPC 的高质量实时阴影。
*场景中的植被、小道具等物体关闭实时阴影投射，或使用开销极低的斑点阴影（Blob Shadow）。

光照成本高

*对静态场景和静态物体，将复杂的光照、阴影及全局光照效果预先烘焙到 Lightmap 中，在运行时直接采样，减少实时计算。
*对动态物体或关键角色，可保留少量实时光照以保证视觉效果，同时尽量降低分辨率和范围。

*建筑室内的光影效果，包括间接光照和柔和阴影，全部预先烘焙完成，运行时直接采样。
*对墙壁、地板、天花板等静态物体使用 Lightmap，减少实时光照计算。
*对门窗开关或移动物体，可使用预设阴影或简单动态光源代替复杂实时光影。

*交互设计过于复杂

*保留功能性交互（如开门进入新区域），减少无意义的装饰性交互。
*对以漫游为主的场景，突出 “探索 + 关键触发” 的体验节奏，保持沉浸感和可玩性。
*用视觉/音效反馈代替复杂交互。

*房间切换 / 门窗交互：仅保留必要的开关动作，用作区域过渡。
*场景漫游为主：减少与体验主线无关的操作，例如装饰物件的点击。
*低交互场景优化：可通过灯光变化、环境音效或路径引导，替代复杂交互。



*问题类型

*优化建议

*示例

角色过多、动作复杂

*减少同屏角色数量，控制渲染和计算负荷，保证帧率稳定。
*限制骨骼动画数量与复杂度，可使用预烘焙动画或 LOD 动画。

*场景中只保留一个主角，突出核心交互和视觉焦点。
*去掉多个 AI 漫游角色，减少不必要的动画负荷。

粒子特效消耗大

将高开销的粒子特效替换为低成本替代方案，如动画贴图或帧动画（Sprite Sheet）。

草丛摆动、烟雾或火焰等效果，用帧动画替代实时粒子特效。



*问题类型

*优化建议

*示例

交互过多

*精简场景中的交互点，避免 “每个物体都可交互”，仅保留关键功能性交互。
*对非核心交互，使用视觉或音效提示代替真实操作，保持场景丰富感而不增加操作复杂度。

*保留 “开灯” 操作，确保用户可以控制环境光照。
*去掉 “每本书都能阅读” 等低价值交互，避免重复操作分散注意力。
*通过环境反馈（如光效变化、声音提示）替代不必要的点击动作。
