了解 ECS 架构
========================================
实体-组件-系统（Entity-Component-System，ECS）架构是一种面向数据（Data Oriented Design, DOD）的架构模式，通过数据与逻辑分离的方式提升性能与可扩展性，广泛应用于游戏引擎、大规模模拟和 XR 等高性能场景。PICO Spatial SDK 采用定制化的 ECS 架构，在保持高效的同时融入了部分面向对象设计（Object Oriented Design，OOD）的思想。
*DOD vs OOD
*DOD 与 OOD 的说明和区别如下：
*
*核心要素
*ECS 架构由三个核心要素构成：
*实体（Entity）：仅作为组件的容器。
*组件（Component）：纯数据结构，用于存储实体的状态或属性。
*系统（System）：负责实现操作的逻辑。例如，查询符合条件的实体，并读取和修改其组件数据。
该架构遵循数据与逻辑分离、单一职责和系统隔离原则，适用于需要高性能、高扩展性和模块化设计的场景。
*应用场景
ECS 架构的典型应用场景如下：
*大量动态实体的交互；
*复杂算法，如程序化生成、路径寻址、动态 AI、复杂物理计算、粒子系统；
*高并发网络场景，对网络速度和稳定性要求高，如多人竞技类游戏；
*性能密集型项目，如数字孪生、大规模模拟；
*性能要求高的设备，如移动设备、XR 头显。
*PICO Spatial SDK 的 ECS 架构设计
*PICO Spatial SDK 采用 ECS 架构来管理和更新 3D 场景，并在传统 ECS 的基础上融入部分 OOD 思想，使架构既保持高性能，又更灵活易用。其核心设计如下：
*层级结构
*一个空间应用包含多个空间容器（WindowContainer 或 Stage），每个容器对应一个场景（Scene）。
*每个场景包含多个实体，每个实体可挂载多个组件。
*实体本身也实现了部分通用功能，减少重复开发。
*逻辑执行
*你可以自定义系统，重写其 update 方法（注册后每帧自动调用）。
*在 update 中，系统可以查询目标实体，获取其组件并修改数据，从而驱动场景更新。
* 
*核心要素在 PICO Spatial SDK 中的实现
*Entity、Component 和 System 类在 PICO Spatial SDK 中的具体实现如下：
*实体
*Entity 表示一个对象的实体，本质上是若干 Component 的容器。在 PICO Spatial SDK 中，Entity 除了包含 ID 信息，还维护一个组件集合（ComponentSet），用于记录、添加和删除所挂载的 Component。
在严格定义的 ECS 架构中，Entity 本身不包含任何属性或逻辑，仅通过所组合的 Component 来体现其特性。而 PICO Spatial SDK 对此进行了扩展，在 Entity 类中加入了一些通用的属性和方法。这样可以避免在创建 Entity 示例时反复绑定必要的 Component 和 System，使你能够更灵活地使用 Entity 的常见功能。
*组件
*Component 表示与 Entity 相关的、具有特定格式的数据。在 PICO Spatial SDK 中，内置的 Component 包括 3D 模型组件、空间变换组件、渲染组件、物理组件、动画组件等，用于满足大多数开发场景和需求。除此之外，你还可以创建自定义 Component，用于存储特定功能的数据，从而扩展系统能力。有关内置组件的详细介绍，参考《内置组件》；有关自定义组件的使用，参考《自定义系统和组件》。
*系统
System 表示每一帧都会执行的行为逻辑，用于读取和更新 Component 数据。在 PICO Spatial SDK  中，System 类提供了 update(context: SceneUpdateContext) 方法，System 注册后会在每一帧自动调用该方法。
你可以把一些特定的行为逻辑组合封装到一个自定义的 System 中，并在其 update 方法中，通过场景查询目标实体，获取对应的 Component，持续修改和更新其数据，从而驱动场景的动态变化。

特点

DOD

强调尽量将数据和逻辑分开，利用现代 CPU 的 SIMD 指令，优化数据布局设计（如结构体对齐 2 的幂、内存按页对齐、冷热数据分割等）。

有助于减少 Cache Miss 的次数，在一定程度上提升程序运行效率，并增强代码的逻辑可复用性和可扩展性。

OOD

数据和逻辑通常存放在同一个类中。

在某些高性能开发场景中，层层抽象出对象的过程会造成代码臃肿，运行效率降低。
