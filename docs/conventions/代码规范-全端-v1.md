# PICO 播控系统 代码规范（全端）v1

> 本文档与《Unity C# 代码规范》（团队已有）配套，覆盖其余各端。
> 章节风格、红线写法、评审清单形式与 Unity 规范保持一致；评审时逐条对照。
> 仓库内放置位置：`docs/conventions/`（本文件 + Unity 规范），Claude Code 与 Kimi 评审均以仓库内版本为准。

## 0. 技术栈总览

| 端 | 技术栈 | 适用规范 |
|---|---|---|
| VR 端 Agent | Android / Kotlin | 第 3 章 |
| 云端平台 | .NET 8 / ASP.NET Core / EF Core / MySQL / Redis | 第 4 章 |

## 1. 通用规范（所有端适用）

### 1.1 命名总则

- 一律英文命名，禁止拼音（`jindu`、`saomiao` 评审打回），专有名词除外。
- 各端大小写遵循本章总表，与语言惯例冲突时以语言惯例为准：

| 元素 | 规则 | 示例 |
|---|---|---|
| 类型 / 类 / 接口 / 枚举 | PascalCase（C++ 按 UE 前缀规则） | `LaunchRecord`、`IQuotaService` |
| 方法 / 函数 | PascalCase（C#、C++）/ camelCase（Kotlin、Python 用小写蛇形 `send_msg`） | `VerifyQuota()` |
| 变量 / 参数 | camelCase（Python 蛇形） | `deviceSn` |
| 常量 | 全大写 + 下划线 | `MAX_RETRY_COUNT` |
| bool | Is / Has / Can / Should 开头，读出来必须是判断句 | `isOnline`；禁止 `isNotOnline` 双重否定 |
| 协议字段（跨端 JSON） | camelCase，各端不得改名 | `launchId` 不得写成 `launch_id`、`LaunchId` |

### 1.2 注释

- 写「为什么」，不写「是什么」。
- 标记注释必须带认领人：`// TODO(LZ): 待接入真实签名校验`；无认领人的 TODO / FIXME / HACK 评审打回。
- 注释掉的死代码禁止提交——要么删除，要么留 TODO 说明。
- 公开 API / SDK 对外方法必须有文档注释（各语言标准格式：C# XML、Kotlin KDoc、Python docstring）。

### 1.3 通用禁止项（全端红线）

1. 魔法数字——数字都要有常量名或注释。
2. 空 catch / 吞异常——最低限度也要记录日志。
3. 密钥、token、凭证硬编码——一律走配置/密钥管理，不进代码库、不进日志。
4. 提交编译不过的代码；提交前本地自测。
5. 复制粘贴超过 10 行的重复代码——抽方法。
6. 调试日志直接调系统输出（`Console.WriteLine`、`println`、`print`）进正式分支——统一走日志工具类，可全局开关、可分级。

## 2. Git 与协作规范

### 2.1 分支模型

```
main          受保护，只接受 MR，对应可交付版本
develop       集成分支，日常合入
feat/M1-02-agent-launch    功能分支 = 一张任务卡一个分支
fix/xxx                   修复分支
```

- 一张任务卡一个分支、一次只做一件事；分支名带任务卡号。
- 里程碑完成后 develop 合入 main 并打 tag：`v0.1-m1`。

### 2.2 提交信息格式

```
[类型][任务卡号] 一句话说明

[功能][M1-02] Agent 实现 LAUNCH_APP 指令拉起与 ACK
[修复][M2-01] 修复断网补传队列重复上报的问题
[优化][M2-03] 账本查询改用索引，降低全表扫描
[重构][M1-04] 抽取指令校验到独立拦截器
[测试][M1-02] 补充 msgId 重放的幂等用例
[文档][M0-01] 更新技术验证清单结果
```

- 类型：功能 / 修复 / 优化 / 重构 / 测试 / 文档 / 资源。
- 无任务卡号的提交（杂项）允许，但同一 PR 内必须有主任务卡号。
- 禁止提交编译不过的代码。

### 2.3 Code Review 流程

```
提交前自测（含协议仿真器互通）→ 提 MR → Kimi 按评审清单逐条过 → 通过合并 / 打回修改
```

- MR 描述必须使用协作协议中的「回报格式」五小节（变更摘要/文件清单/测试报告/与规格偏差/待确认问题）。
- 评审打回项逐条修复后在 MR 中引用编号回复。

## 3. Android（Kotlin）规范 —— VR 端 Agent

### 3.1 命名与组织

- 遵循 Kotlin 官方惯例：类 PascalCase，函数/变量 camelCase，常量 `const val` 全大写下划线。
- 包名全小写：`com.{公司}.broadcast.agent.{模块}`，模块：`command`（指令通道）/ `control`（设备管控）/ `billing`（记账）/ `quota`（额度）/ `monitor`（前台监听）/ `capture`（画面采集）/ `guard`（防篡改）。
- 一个文件一个顶层类；单文件不超 500 行，超出必拆。

### 3.2 线程与协程（红线区）

1. 后台任务一律用协程（`viewModelScope` / 自定义 `SupervisorJob`），禁止裸 `Thread`、禁止 AsyncTask。
2. 禁止 `runBlocking` 出现在主线程路径——卡死 UI 且掩盖问题。
3. 协程异常必须经 `CoroutineExceptionHandler` 或 try/catch 收敛，不得静默消失。
4. 长驻服务（指令通道、心跳、前台监听）用前台 Service + WakeLock 策略保活，并配合 `pbsAppKeepAlive`；进程重建后必须能自愈恢复各通道。

### 3.3 账本与存储（计费红线，最高优先）

1. Room/SQLite 实现，`launchId` 建**唯一索引**——幂等靠数据库约束，禁止「先查再插」。
2. 账本行写库前生成签名；密钥走 Android Keystore，禁止硬编码、禁止 SharedPreferences 明文。
3. 账本 DB 文件加密（SQLCipher 或等效方案）。
4. 补传队列只认 uploadStatus 状态机：未上传 → 已上传 → 已对账；失败留在队列，禁止丢弃。
5. 任何「先拉起应用、后扣额度」的顺序都是事故——必须先校验额度。

### 3.4 权限与 TobService 调用

- TobService 调用集中封装在 `control` 模块的 `PicoTobService` 门面类，业务代码不得直接散落调用——便于换设备适配和统一兜底。
- 每个 TobService 调用必须处理「设备不支持 / 无权限 / 服务未绑定」三种失败，失败产生告警事件而不是只打日志。
- 高风险接口清单（`pico_advance_interface` 相关）集中登记在 `docs/` 一份清单里，新增必须登记。

### 3.5 日志

统一 `AgentLog` 工具类：分级（D/I/W/E）、全局开关、按天滚动落盘（供真机验收取日志）、敏感字段（SN 全号、token、账本明文）脱敏。

## 4. .NET 8 规范 —— 云端平台 + 门店本地服务

### 4.1 分层（物理隔离，对应目录结构）

```
Api/            控制器、DTO、WSS/MQTT 网关接入
Application/    用例编排、事务边界
Domain/         实体、领域规则（额度、免单判定在这里）
Infrastructure/ EF Core、Redis、消息、外部服务
```

- 依赖方向只能：Api → Application → Domain ← Infrastructure。Domain 出现 EF Core 的 using 视为架构事故，评审打回。
- DTO 与领域实体分离；Api 层不得直接把实体序列化出去。

### 4.2 异步与并发（红线区）

1. async/await 一路到底，禁止 `.Result` / `.Wait()` / `.GetAwaiter().GetResult()`——死锁与线程饥饿重灾区。
2. 计费写路径必须显式事务 + 乐观/悲观并发控制；额度扣减用数据库条件更新（`WHERE balance >= 1`）或分布式锁，禁止「读出来减一再写回」。
3. 幂等靠唯一约束 + 捕获冲突异常，不靠在代码里先 SELECT。

### 4.3 API 与错误码

- REST 响应统一包裹：`{ code, message, data }`；`code=0` 成功，业务错误码分段：
  - `1xxx` 鉴权/账号；`2xxx` 设备/指令；`3xxx` 额度/计费；`4xxx` 内容/分发；`5xxx` 系统。
- 错误码登记表放 `docs/specs/error-codes.md`，新增必须登记，禁止散落魔法码。
- 指令协议字段 camelCase，与设备端逐字一致（见第 7 章）。

### 4.4 数据访问

- EF Core 迁移（Migration）必须随代码一起提交；禁止手改生产库。
- 账本表只 INSERT 不 UPDATE/DELETE（审计不可变），对账冲正用反向记录。
- 所有表带 `created_at` / `tenant_id`；跨租户查询必须显式带租户过滤，全局过滤器默认开启。

### 4.5 配置与日志

- 配置走 `appsettings.{环境}.json` + 环境变量，机密（签名私钥、DB 密码）只走环境变量/密钥服务。
- 日志用结构化日志（Serilog/NLog），带 traceId 贯穿指令全链路（控制端 → 云端 → Agent 的 msgId 即 traceId）。

## 5. UE C++ 规范（内容端，一期简要、二期细化）

- 命名遵循 Epic 官方：UCLASS 前缀 `U`、AActor 前缀 `A`、结构体 `F`、枚举 `E`、接口 `I`；bool 前缀 `b`。
- 暴露给蓝图的成员用 `UPROPERTY` 并写 `Category`；生命周期遵循 `BeginPlay` / `EndPlay`，事件注销成对（参考 Unity 规范 3.4 同款原则）。
- 与播控 SDK 的桥接代码集中在 `BroadcastBridge` 模块，游戏逻辑不直接碰 JNI/平台 API。
- 其余沿用 Epic Coding Standard；二期出细则。

---

## 6. Python 规范（仿真器与工具）

- PEP 8 + snake_case；零外部依赖优先（标准库 + websockets）。
- 仿真器用例断言行为而非日志；输出格式 `[PASS] AC2: ...` / `[FAIL] AC3: ...` 逐条对应任务卡。
- 脚本必须支持重复运行（幂等、无残留状态依赖）。

---

## 7. 协议与接口规范（跨端，最高一致性要求）

1. **字段命名**：JSON 一律 camelCase，全端逐字一致——`launchId` 在任何一端写成 `launch_id` / `LaunchId` 都是评审打回项。
2. **兼容性**：协议只加字段不改字段、不删字段；破坏性变更升协议版本号（`"version": 2`），新旧版本并存一个里程碑。
3. **指令三件套**：每条指令必须带 `msgId`（幂等键）、`ts`（时间戳）、`ACK` 回执；ACK 结构统一 `{ msgId, result, errorCode, detail }`。
4. **唯一权威**：协议定义以设计文档 §6 与任务卡为准；任何端发现协议问题走 STOP 流程提裁决，禁止私自改协议适配自己。

## 8. 禁止清单（全端红线汇总，评审逐条对照）

1. 拼音命名。
2. 魔法数字 / 魔法错误码。
3. 空 catch 吞异常。
4. 密钥/凭证硬编码、敏感信息进日志。
5. 提交编译不过的代码；注释掉的死代码。
6. 系统原生输出直接进正式分支（绕过日志工具类）。
7. 「先查再插」做幂等——必须用数据库唯一约束。
8. 先拉起应用后扣额度——顺序即事故。
9. 账本记录 UPDATE/DELETE——只能 INSERT + 反向冲正。
10. async void（C#，事件处理器除外）/ `.Result` 阻塞 / `runBlocking` 主线程（Kotlin）。
11. 跨层反向依赖（Domain 引 Infrastructure、Core 引 Gameplay）。
12. 私自改协议字段名适配本端。
